## 1. Goal

Replace the NPoco `MediaRepository` with an EF Core repository and move `MediaService` onto the asynchronous, Guid-keyed engine that `ContentService` and `ElementService` already run on, delivered as a sequence of small, independently reviewable PRs, following the element campaign (`../ef-core-element-repository/CAMPAIGN.md`).

When the campaign is finished:

- `IMediaRepository` is an EF Core, async, Guid-keyed contract: `IMediaRepository : IAsyncContentRepository<IMedia>` plus `GetMediaByPathAsync`. No `int` id, no `IQuery<T>`, no `out` total anywhere on it.
- `MediaRepository` lives in `src/Umbraco.Infrastructure/Persistence/Repositories/Implement/EFCore/` and is a thin subclass of `AsyncContentRepositoryBase` (the wide, non-publishable base), roughly the size of `ElementRepository` (about 170 lines) plus the media-only members (path lookup, media version row, delete clauses).
- `IMediaService` has the shape of `IContentService` minus publishing: every member async with a trailing `CancellationToken`, Guid keys, Guid user keys, `Attempt<TStatus>` on writes, `PagedModel<T>` with `skip`/`take` on paging. It no longer inherits the sync `IContentServiceBase<IMedia>`.
- `MediaService : ContentServiceBase<IMedia, IMediaType>, IMediaService`, a thin subclass of a new wide service base that `PublishableContentServiceBase` also derives from. No synchronous bridging member survives on it.
- Every media integration and unit test fixture is green on SQLite; the SQL Server run differs from the parent branch only by the known-flaky search jobs (§3).

Out of scope, by decision (§8): members (`MemberRepository`, `MemberFilterRepository`, `MemberService`, the sync `IContentServiceBase<T>` and NPoco `ContentRepositoryBase` they still use), `DatabaseCacheRepository` (HybridCache), `ContentNavigationRepository`, `EntityRepository`. The `Async` prefix on `AsyncContentRepositoryBase`, `IAsyncContentRepository` and `IAsyncContentServiceBase` therefore stays until the members campaign retires the sync twins.

## 2. Why the shape is different from the element campaign

Elements were publishable, so the engine already existed and the service swap was one step. Media is not publishable, and that changes both tiers:

- Repository tier. The generic read, write, delete and naming machinery that the element campaign hoisted out of `DocumentRepository` landed in `PublishableContentRepositoryBase` (2 381 lines), typed on `ContentRow<TEntityDto : IPublishableContentDto, TContentVersionDto : IContentVersionDto>`. Media has no entity table (only `umbracoNode`, `umbracoContent`, `umbracoContentVersion` and `umbracoMediaVersion`, whose version row carries just `id` and `path`), no published flags and no culture variations. It cannot sit on that base, and the wide `AsyncContentRepositoryBase` (905 lines) has helpers but no read or write path (its `GetChildrenAsync`, `GetDescendantsAsync`, `GetRootContentAsync`, `GetRecycleBinAsync`, `GetPagedRecycleBinAsync`, `GetAllVersionsAsync`, `GetVersionAsync` are abstract, and the delete it inherits from `AsyncEntityRepositoryBase` is a `db.Set<TEntity>()` call that cannot work for an interface entity). So this campaign hoists the generic machinery one level further down, into the wide base, with row types that no longer require an entity DTO or a published flag. The publishable base keeps only publishing.
- Service tier. The async engine is `PublishableContentServiceBase<TContent>` with `where TContent : IPublishableContentBase`, and the tree operations (move, move to recycle bin, empty recycle bin, sort, create, children, descendants, ancestors, root, by level) are not on it at all: `ContentService` implements them against `IDocumentRepository` and `ElementService` has none. Media needs all of them. So this campaign introduces the wide service base `ContentServiceBase<TContent, TContentType>` carrying the generic members from `PublishableContentServiceBase` and the tree operations from `ContentService`, with notification hooks for the kinds that differ, and `PublishableContentServiceBase` becomes its publishing subclass.

Decision (§8): hoist first, in both tiers, then add media as thin subclasses. The alternative (a self-contained EF Core `MediaRepository` and a self-contained async `MediaService`, which is the NPoco layout today) was rejected: it duplicates about 1 200 lines of read, write, paging and tree logic between documents and media, and every upstream fix would then have to be hand-walked into a second copy on every merge-up. This branch has already lost five fixes to exactly that failure mode (memory `project_async_fork_merge_hazard`).

## 3. Rules that apply (read even if you know the repo)

Repo-wide: `/CLAUDE.md`, `/src/Umbraco.Core/CLAUDE.md`, `/src/Umbraco.Infrastructure/CLAUDE.md` §12 (EF Core DTO guide), `/tests/Umbraco.Tests.Integration/CLAUDE.md`. Branch learnings: `../LEARNINGS.md`.

Branch-specific decisions already made during the document and element campaigns. Do not relitigate them:

1. Breaking changes are allowed on this branch. The work ships in Umbraco 20 even though the integration branch is still named `v18/feature/ef-core-repositories`; any `[Obsolete]` text that is unavoidable says "Scheduled for removal in Umbraco 22". Change signatures directly; no obsolete-constructor or obsolete-overload staging; delete sync members outright. Review bots flag breaking changes on every PR; answer once that they are allowed here.
2. Every new repository or service member takes Guid keys, never int ids, even when the column and first caller are int-based. Resolve internally. `IIdKeyMap` is edge code: a controller, a cache refresher payload, a value converter or a user-group start node may resolve an int at the boundary; a repository or a service base never takes one. The only `int` identifiers allowed are version ids (`umbracoContentVersion` is int-identified by decision) and `level`.
3. Do not port `IQuery<T>`. The EF Core side exposes purpose-built query shapes only (`GetChildrenAsync`, `GetDescendantsAsync`, `GetPagedOfContentTypesAsync`, `GetByLevelAsync`, ...). Re-express each `Get(query)` and each `filter` argument against one of those; where a caller's predicate cannot be expressed, add a purpose-built member rather than a predicate parameter.
4. EF Core code never references a NPoco repository class, not even a static helper. Copy the helper.
5. `UmbracoDbContext` is globally NoTracking. Read-then-mutate-then-save needs `.AsTracking()`. Materialisation bypasses DTO setters; use `UsePropertyAccessMode(Property)` where setter logic matters. A row whose id the scope's context already tracks cannot be `Update`d; use an update statement (element PR 3 trap).
6. Never use `is`-patterns inside an EF Core query lambda (CS8122), and never a `Contains` on an array inside one (copy to a `List<T>` first). Modern C# (property patterns, `is null`, collection expressions) everywhere else in files this campaign rewrites.
7. No `autoComplete: true` on scopes; call `scope.Complete()` explicitly.
8. `CancellationToken` is the last parameter on every new async member. Adding a required trailing token after existing optional parameters is CS1737: make the optional parameters required instead of moving the token forward.
9. A new `*Async` member goes on the interface tier where its sync counterpart was declared (wide `IAsyncContentRepository<T>` / `IAsyncContentServiceBase<T>` versus publishable-only `IPublishableContentRepository<T>` / `IPublishableContentService<T>` versus `IMediaService`).
10. Async-named scaffolding (`IAsyncMediaRepository`, `AsyncMediaRepository`) stays pure async; no sync bridges on it. The names are temporary and get renamed in PR 7. The wide service base takes its final name `ContentServiceBase<TContent, TContentType>` at once: no sync class of that name exists (only the sync interface `IContentServiceBase<T>`, which members still use).
11. EF Core DTOs are plain table rows: no navigation members, no setters on the DTO interfaces, factories take rows as parameters, and no row is mutated after it is built (build it once its values are known). The `BuildBaseQuery` join projection uses object-initializer syntax, never a positional record constructor, so ordering translates.
12. Style: Allman braces, braces on every body, no section-header or Arrange/Act/Assert comments, no provenance comments ("mirrors NPoco's ..." is a provenance comment: do not add new ones), `[]` for empty enumerables. Git Bash `sed -i` strips CR from CRLF files; use a line-ending-preserving script for bulk edits.
13. Content versions have no Guid key. Never reintroduce a version key.
14. `Constants.System.RootKey` is null. `IIdKeyMap` cannot resolve `-1`; root-level handling must special-case `null` parent keys. `umbracoNode` id `-1` is a real row whose `UniqueId` is `RootSystemKey`; a parent self-join must special-case root or it leaks that key as `ParentKey`.
15. SQL Server search integration jobs are flaky on every branch. Diff the failed list against the parent branch's last run before treating a failure as a regression.
16. A shared base hardcodes the first entity's flavour. Before a cutover, grep the base for constants, notification types and recycle bin ids that belong to the entity that got there first, and turn them into hooks (element PR 5 found `ContentDeletingVersionsNotification` and the document recycle bin id hardcoded that way).
17. "Unreferenced" is not "removable". `ContentRepositoryBase` (NPoco) is a public class, so its protected members are public API even with zero callers; check the declaring type's accessibility before deleting an orphan. Internal members with zero callers may go.

Contract rules (the shape every member on the async side must have):

- Repository read surface is `IAsyncReadWriteRepository<Guid, TEntity>`: `GetAsync(Guid? key, ct)`, `GetManyAsync(Guid[] keys, ct)`, `GetAllAsync(ct)`, `ExistsAsync(Guid key, ct)`, `SaveAsync(entity, ct)`, `DeleteAsync(entity, ct)`. There is no `Get(int)`, no `GetMany(params int[])` and no `GetAll(params int[])`.
- No `IQuery<T>` parameter anywhere, no `out long totalRecords`, no `pageIndex`/`pageSize`. Paged members take `int skip, int take, Ordering? ordering` and return `PagedModel<T>`.
- Users are identified by `Guid userKey`, never `int userId`; resolve through `IUserIdKeyResolver` inside the service.
- Service members that can fail return `Attempt<TStatus>` or `Attempt<TResult, TStatus>` with a bespoke `*OperationStatus` enum from `Services/OperationStatus/` (`ContentSaveOperationStatus`, `ContentDeleteOperationStatus`, `ContentMoveOperationStatus`, `ContentMoveToRecycleBinOperationStatus`, `ContentEmptyRecycleBinOperationStatus`, `ContentSortOperationStatus`, `ContentSortChildrenOperationStatus`, `ContentVersionOperationStatus`, `ContentDeleteOfTypesOperationStatus`). No `OperationResult`, no thrown exceptions for expected failures (a missing or trashed parent is `ContentMoveOperationStatus.ParentNotFound` / `ParentTrashed`, not an `InvalidOperationException`).
- Every async member takes `CancellationToken` last and is named `*Async`. No sync bridge (`Task.FromResult(sync)`, `.GetAwaiter().GetResult()`) survives on a class that implements the async contract.
- Notifications are published with `PublishCancelableAsync`/`PublishAsync` where the engine already does so; mirror `ContentService`, not the sync `MediaService`.

What this campaign retires: the 49 members of `IMediaService` (plus 2 extension methods) in their current shape, of which 45 are sync and 20 have no caller outside `MediaService` itself; the sync, int-keyed `IMediaRepository` with its 26 members; the nested `MediaByGuidReadRepository` in `MediaRepository.cs` (the "decouple MediaByGuidReadRepository" task from the backlog is closed by this campaign, not done: with Guid-only contracts there is nothing left to decouple). PR 6's acceptance includes a grep proving none of the old shapes remain.

Build and test discipline:

- `dotnet build umbraco.sln` fresh before trusting any green. With the .NET 11 SDK the first solution build can fail with MSB3030 on `appsettings-schema.Umbraco.Cms.json`; run it again.
- Never trust `--no-build`. Rebuild the test project itself after a subagent edits production code.
- A full `--no-incremental` build rewrites `package-lock.json` files, `src/Umbraco.Web.UI.Client/src/libs/localization-api/known-keys.*.generated.ts` and `src/Umbraco.Web.UI.Login/public/mockServiceWorker.js`; `git checkout --` them before committing.
- `dotnet format style <project>.csproj --diagnostics IDE0005 --severity info --include <touched files>` per project, touched files only.
- `git status --short` before every commit; investigate stray diffs.
- Tests for a fix must fail before the fix. Verify by reverting the production change once. A hoist PR is verified the other way round: the fixtures of the entities already on the engine must stay green at unchanged counts, and a normalised diff of each moved method body against its origin must show only the hook substitutions.
- Locally, run the tests the change touches plus the red-first proof. Full suites run on the pipeline.
- EF Core migrations: use the `/umb-ef-core-empty-migration` skill. `appsettings.Local.json` overrides environment variables (`Program.cs` adds it last); move it aside while running `dotnet ef`, restore afterwards. The scaffolder may emit `_<timestamp>_Name` as the class name; rename it in the Designer file to the plain name. The global `dotnet-ef` tool must match the package's EF Core version (11.0.0 since 20-11-2026). When a merge-up brings in another migration on the same snapshot, the PR's own unmerged migration is regenerated on top; the shared one is never touched (memory `project_ef_migration_merge_drift`).
- When the backoffice `node_modules` are stale after a merge-up, build with `-p:UmbracoBuild=1`.
- After a merge of `main` into the integration branch, run the merge audit (memory `project_merge_audit_procedure`) before cutting the next PR: sync hunks land silently in the renamed async files, and upstream fixes to `MediaService`/`MediaRepository` (sync) must be walked by hand into the async twins once PR 6 has merged.

Process (validated on two campaigns):

- Research before delegating: read the NPoco reference method end-to-end and the EF Core precedent, then write the subagent brief with verbatim snippets and `file:line` references.
- One phase per subagent, TDD inside the phase, and independently re-verify every claim (`git diff --stat`, rebuild, rerun the full fixture, read the riskiest code). Investigation agents' negative claims ("nothing else uses X") are leads, not facts.
- After every PR's implementation, spawn two agents in one message: an independent reviewer (behaviour, convention alignment, duplication) and a mechanical test runner. Unconditional, even for small PRs.
- Stacked PRs: point the upper PR at the lower PR's branch; after the lower one is squash-merged, `git rebase --onto <integration> <old base>` the upper PR's own commits and force-push with a lease.

### 4b. Media behaviours the port must keep, and the ones it deliberately changes

Keep (parity with the NPoco service and repository; each gets a test in PR 4 or PR 6):

1. `MediaSavingNotification.IsSorting = true` on the saving notification raised while sorting. Three handlers skip file metadata extraction on it (`FileUploadMediaSavingNotificationHandler.cs:45`, `SvgFileUploadMediaSavingNotificationHandler.cs:36`, `ImageCropperPropertyEditor.cs:232`; upstream #24349). There are no `MediaSorting`/`MediaSorted` notifications.
2. One `MediaDeletedNotification` per deleted item, descendants deepest first, each carrying the full entity: this is what deletes media files (`FileUploadContentDeletedNotificationHandler`, `ImageCropperPropertyEditor`; recycle-bin protection suffixes files on `MediaMovedToRecycleBinNotification` and un-suffixes on `MediaMovedNotification` using `OriginalPath`).
3. `MediaRefreshNotification` published by the repository on every persist (HybridCache depends on it).
4. `umbracoMediaVersion.path` written on every save from the `umbracoFile` property through `MediaUrlGeneratorCollection.TryGetMediaPath`; `GetMediaByPath` strips a `_{w}x{h}` resize suffix before matching the column exactly.
5. Tags set on every save (the publishable base sets them only when publishing).
6. Media version deletion is a no-op at the repository (one version per media item); the service still publishes `MediaDeletingVersionsNotification`/`MediaDeletedVersionsNotification` around it.
7. Single `Save`: the Guid v7 check (`media.Key.Version == 7 && !_mediaPathScheme.SupportsGuid7` fails the save) and the duplicate-key check for new items. `MediaEditingService` maps both to `ContentEditingOperationStatus.InvalidKey`/`DuplicateKey`.
8. `DeleteMediaOfTypes` moves every descendant whose type is not being deleted to the recycle bin (not only direct children, as `ContentService` does) before deleting the item.
9. `EmptyRecycleBin` has no `DisableDeleteWhenReferenced` relation check.
10. Unique names per parent on every save, with the sibling fetch narrowed to names sharing the base text (#23447; large flat media libraries are the case it was written for; the EF Core base lost it, see PR 3b).

Change (adopting the engine's behaviour; each is recorded in §8 and gets a test):

1. Expected failures become statuses: a missing or trashed parent on move is `ParentNotFound`/`ParentTrashed` instead of `InvalidOperationException`; a cancelled move to the recycle bin is `CancelledByNotification` instead of being reported as success; `CreateMedia`'s `ArgumentException` for an unknown type alias stays an exception (programming error), as in `ContentService.CreateAsync`.
2. `MoveAsync` to the current parent is a no-op success (the sync media service re-saved everything).
3. `WriterId` is set on sort and on bulk save; the sort audit is written per changed item with the item id (today: once, object id 0).
4. `EmptyRecycleBinAsync` publishes the cancelable bulk `MediaDeletingNotification` before deleting, as the engine does for documents, and uses the scope's event messages for the emptied notification (today a fresh `EventMessages`).
5. Restoring an item out of the recycle bin without its descendants sets `ParentKey` on the re-homed children (today only `ParentId`).
6. Media names come from `umbracoContentVersion.text` on read, as for documents and elements (today `umbracoNode.text`). Both columns are written identically and media has one version, so no observable change; a test asserts they agree after a rename.

## 10. Working across machines (personal handover area)

The orphan branch `campaign/ef-core-element-repository` holds every campaign folder, `LEARNINGS.md`, `grand-plan/`, the memory sync scripts and the `memory/` snapshot. It is checked out as a worktree at `.claude/campaign/` inside the main checkout; `.claude/*` is gitignored there, so the main tree never sees it and it cannot leak into a PR.

| File | Purpose |
|---|---|
| `ef-core-media-repository/CAMPAIGN.md` | This plan. |
| `ef-core-media-repository/status.json` | Progress source of truth; rendered by the artifact. |
| `ef-core-media-repository/progress.html` | Page source for the artifact. Only changes when the page layout changes. |
| `sync-memory.sh`, `sync-memory.ps1` (branch root) | `pull` copies `memory/*.md` into the local Claude Code memory directory for the main checkout; `push` copies the local directory back. Newer file wins. Both find the main checkout through `git rev-parse --git-common-dir` and derive the memory directory the way Claude Code names project folders; pass it explicitly as the second argument (bash) or `-MemoryDir` (PowerShell), or set `CLAUDE_MEMORY_DIR`, if the guess is wrong. |
| `memory/` (branch root) | Snapshot of the Claude Code memory files for this repository. Treat it as read-only on disk; edit the live memory and `push`. |

First-time setup on a machine (run from the main checkout):

```
git fetch origin campaign/ef-core-element-repository
git worktree add .claude/campaign campaign/ef-core-element-repository
.claude/campaign/sync-memory.sh pull        # Linux/macOS
.claude\campaign\sync-memory.ps1 pull      # Windows (PowerShell)
```

Routine: `git -C .claude/campaign pull` and `sync-memory.sh pull` at the start of a session on a machine that may be behind; `sync-memory.sh push`, commit inside the worktree and push the branch at the end of every session (§6 step 13). Status changes travel in the same commit. If two machines both changed `status.json`, keep both sides' task and log updates; the `updated` date is the later one.

Agents: when a tool reports the working directory as `.claude/campaign`, you are inside this worktree. Code work happens in the main checkout one level up; only plan, status and memory files are committed here.
