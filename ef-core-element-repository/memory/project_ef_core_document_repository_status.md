### Bug fixed by a second independent review round: missing pagination tiebreaker (2026-08-05)
A second review pass (same 3-axis brief, run fresh with no context from the first) caught a real, pre-existing bug surfaced by the recycle-bin work: the shared `ApplyDocumentOrdering` helper (used by `GetChildrenCoreAsync`, `GetDescendantsCoreAsync`, AND the new `GetPagedRecycleBinAsync`) and the three duplicated `FetchCultureNameOrdered` local functions order purely by the requested field with no secondary tiebreaker. NPoco's equivalent (`ContentRepositoryBase.PreparePageSql`, lines 467-474) unconditionally appends `ORDER BY umbracoNode.id` after any user ordering, citing a real historical bug (**http://issues.umbraco.org/issue/U4-8831**) — without it, ties in the sort field make paged results unstable/duplicated across separate fetches.

This bug pre-dated the recycle-bin work (it was already live in `GetChildrenCoreAsync`/`GetDescendantsCoreAsync`), but recycle bin is the first call site where it's likely to actually bite: `SortOrder` is only unique per-parent, and the recycle bin aggregates trashed nodes from many different original parents, so `SortOrder` ties are the norm there, unlike children-of-one-parent.

**Fix**: added `.ThenBy(idSelector)` (skipped when already ordering by `"id"`) to `ApplyDocumentOrdering`, and `.ThenBy(joined => joined.node.NodeId)` to all three `FetchCultureNameOrdered` copies. This transitively fixes the same latent bug in the two pre-existing methods too, not just the new one — user explicitly approved this broader scope via `AskUserQuestion` ("fix the shared helper" over "fix only in recycle bin" or "just log a TODO").

**Regression test resolved via a unit test that manipulates NodeId directly (2026-08-05, user-requested follow-up)**: the first attempt at an integration-level regression test failed to discriminate (see [[feedback_sqlite_harness_masks_ordering_tiebreak_bugs]] — SQLite's scan order for freshly-inserted rows coincidentally matches NodeId order regardless of the fix). The user asked for a test that manipulates the NodeId directly; the fix was to test the shared `ApplyDocumentOrdering` helper in isolation rather than through a real database:
- Changed `ApplyDocumentOrdering` from `private static` to `internal static` (safe, behavior-unchanged — needed only so a unit test in a different assembly can call it via `InternalsVisibleTo`). Added an XML `<summary>`/`<remarks>` doc comment since StyleCop's SA1600 requires docs on `internal` members but not `private` ones (this surfaced as a new warning when the modifier changed, fixed by adding the doc comment).
- New file `tests/Umbraco.Tests.UnitTests/Umbraco.Infrastructure/Persistence/Repositories/AsyncDocumentRepositoryOrderingTests.cs` (3 tests): constructs an in-memory `List<OrderingTestRow>` with the row carrying the HIGHER NodeId placed FIRST in the sequence — deliberately decoupling "sequence order" from "NodeId order" in a way a real SQLite integration test cannot (there NodeId is always assigned in insertion order, so the two can never diverge for freshly-created rows). Calls `AsyncDocumentRepository.ApplyDocumentOrdering` directly and asserts ascending-NodeId output for both the default (SortOrder-tied) and "name"-tied cases, plus a third test confirming the `"id"`-ordering case doesn't get a redundant tiebreak appended.

### Publish-scheduling / publish-status methods implemented (2026-08-06)
`AsyncPublishableContentRepositoryBase` (`Persistence/Repositories/Implement/EFCore/AsyncPublishableContentRepositoryBase.cs`) had **11** `virtual` members throwing `NotImplementedException` (not 10 — an earlier gap-analysis artifact undercounted `ClearScheduleAsync`'s two overloads as one). All 11 are now implemented: `GetContentScheduleAsync`, `PersistContentScheduleAsync`, `ClearScheduleAsync` (×2 overloads), `HasContentForExpirationAsync`/`HasContentForReleaseAsync`, `GetContentForExpirationAsync`/`GetContentForReleaseAsync`, `CountPublishedAsync`, `GetContentSchedulesByKeysAsync` — 10 generic in the base class — plus `IsPathPublishedAsync`, overridden concretely in `AsyncDocumentRepository` (the one method NPoco itself implements per-entity-type rather than sharing, since `ElementRepository.IsPathPublished` is a trivial one-liner while `DocumentRepository.IsPathPublished` does a real ancestor path-walk).

`ContentScheduleDto` already existed in EF Core — this was pure repository-method work, no new DTO/migration.

**Key design fix found only by actually trying to compile the generic implementation**: NPoco's `CountPublished`/`IsPathPublished` filter on `TEntityDto.Published` (table-level flag), but the EF Core base class's original `TEntityDto : class` constraint didn't expose that generically. The fix was widening the constraint to `TEntityDto : class, IPublishableContentDto<TContentVersionDto>` (`Persistence/Dtos/EFCore/IPublishableContentDto.cs` — already existed, already implemented by `DocumentDto`, just wasn't used as a constraint yet) — this exposes `NodeId`/`Published` generically. A `protected static IQueryable<NodeDto> PublishedNodes(UmbracoDbContext db)` helper (join `db.Nodes` → `db.Set<TEntityDto>().Where(e => e.Published)`) is shared by `CountPublishedAsync` and `IsPathPublishedAsync`'s override.

**Verified this constraint widening is safe for future implementers, not just convenient now** (user explicitly asked to double-check, since a bare `class` constraint might have been deliberate): it isn't — three pieces of evidence. (1) NPoco's own `PublishableContentRepositoryBase` (the class this was ported from) has *always* required `TEntityDto : class, IPublishableContentDto<TContentVersionDto>` — both its real implementers, NPoco's `DocumentDto` and `ElementDto`, already satisfy it. (2) The only two domain types that could ever instantiate this EF Core base class are `IContent` and `IElement` (the only implementers of `IPublishableContentBase`, the existing `TEntity` constraint) — Media/Members have no publish workflow and would never use this class regardless. Element has no EF Core port yet (no `ElementDto`/`AsyncElementRepository` under `Persistence/*/EFCore/`), but NPoco's `ElementDto` already implements the interface, so its future EF Core port will need to too, independent of this change. (3) `git log -p` on this file shows `TEntityDto`/`TContentVersionDto` both started as bare `class` at the original scaffolding commit (`ca0e6a31cea`); `TContentVersionDto` was tightened to `IContentVersionDto` the moment `PerformDeleteVersionAsync` needed it — `TEntityDto` simply hadn't hit that same trigger until this work. Same incremental-tightening pattern, not a reversal of a deliberate design choice.

**Three real bugs found only by actually running the tests, not by reasoning about the code:**
1. **`ContentService.Publish` rejects publishing a node whose ancestor path isn't itself published** (`PublishResultType.FailedPublishPathNotPublished`) — this is NOT documented anywhere obvious and broke the first draft of two tests (`CountPublishedAsync_IncreasesAfterPublishingAnotherItem`, `IsPathPublishedAsync_DescendantWithUnpublishedAncestor_ReturnsFalse`), both of which tried to publish a child directly while its parent stayed unpublished — the call silently returned `Success = false` and neither test checked the `PublishResult`, so both would have been coincidental false-passes (the exact "test passes for the wrong reason" trap the root `CLAUDE.md` TDD section warns about) had the diagnostic assertion not been added. Fixed by publishing the parent first, then the child, then (for the "unpublished ancestor" case) unpublishing just the parent — unpublishing does NOT cascade to children, so the child's own `Published` flag stays true while the path is no longer fully published. Every `ContentService.Publish`/`Unpublish` call in these tests now asserts `.Success` explicitly.
2. **`UmbracoDbContext` sets `QueryTrackingBehavior.NoTracking` globally** (`UmbracoDbContext.cs:198`) — so a query like `db.ContentSchedules.Where(...).ToDictionaryAsync(...)` returns fresh untracked instances even when entities with the same key are already tracked from an earlier `Add`+`SaveChangesAsync` call in the same ambient scope (the EF Core `DbContext` instance is cached per ambient scope — `EFCoreScope<T>.ExecuteWithContextAsync` reuses one `_dbContext` field across every repository call within one `NewScopeProvider.CreateScope()`, confirmed by reading `EFCoreScope.cs` directly). Mixing an untracked query result with an already-tracked entity of the same key throws `InvalidOperationException: cannot be tracked because another instance with the same key value ... is already being tracked`. Fixed by adding `.AsTracking()` to `PersistContentScheduleAsync`'s existing-rows query — the exact same pattern already established in `PersistUpdatedPropertyDataAsync` (which has its own comment explaining the same override-the-global-default reasoning). **Any new method that reads-then-mutates-then-saves an EF Core entity in this codebase needs `.AsTracking()` — it is not the default.**
3. **`ContentScheduleDto.NodeId` has a real FK to `ContentDto`** — a schedule-isolation test that tried inserting a raw `ContentScheduleDto` row for the recycle bin folder node (id `-20`, a system node with no `umbracoContent` row) hit a SQLite FK violation. Fixed by reusing an existing Document node (`_subpage`, which already has valid `Node`/`Content`/`ContentVersion` rows) and temporarily reclassifying its `NodeObjectType` to `Media` via `ExecuteUpdateAsync`, instead of inserting a fabricated row for an unrelated system node.

TDD followed properly: 20 new tests written against the `NotImplementedException` stubs first (confirmed exact-exception failures), then implemented, then iterated through the 3 failures above until genuinely green.

### Sibling name-uniqueness implemented (2026-08-06)
Replaced the blank-name-only stand-in with a real port of NPoco's `PublishableContentRepositoryBase.SanitizeNames`: literal duplicate-name suffixing, URL-segment collision detection (`" (n)"` suffix when two different names clean to the same URL segment — fixes umbraco/Umbraco-CMS#22070 for the EF Core path too), and per-culture uniqueness for variant content.

**Split, mirroring the schedule/publish-status precedent**: shared orchestration (`SanitizeNamesAsync`, `EnsureInvariantNameExistsAsync`, `EnsureInvariantNameIsUniqueAsync`, `EnsureVariantNamesAreUniqueAsync`, `EnsureUniqueNaming`) lives in `AsyncPublishableContentRepositoryBase` behind two virtual hooks (`EnsureUniqueNodeNameAsync`, `EnsureUniqueVariantNameAsync`; default: literal-duplicate check only, via the pre-existing `SimilarNodeName.GetUniqueName` utility). `AsyncDocumentRepository` overrides both hooks to add the URL-segment check, needing a new `IShortStringHelper` constructor dependency (no obsolete-constructor dance — class still has zero DI registration).

**Important architectural rule surfaced here, applies to all future EF Core repo work**: never reference an NPoco repository class (`DocumentRepository`, `ContentRepositoryBase`, etc.) from EF Core code, even an `internal static` helper method with no other NPoco dependency — those classes are slated for deletion once the migration completes, so depending on them blocks that deletion later. The URL-segment-collision logic was originally implemented as a call to NPoco's `DocumentRepository.EnsureUniqueUrlSegment` (assembly-internal, looked "safe" to reuse since it has no NPoco-specific dependency itself) — the user explicitly rejected this on exactly that basis. Fixed by copying the method's implementation directly into `AsyncDocumentRepository.cs` as a private static method instead. See [[feedback_dont_depend_on_repository_being_replaced]] for the closely related, previously-established rule about not depending on the repository instance being replaced — this extends that same principle to *any* NPoco repository class, not just the one being directly ported.
