While introducing `GetByIdsAsync(IEnumerable<Guid>, CancellationToken)` (replacing `IContentService.GetByIds(IEnumerable<int>)`), declared it on `IAsyncContentServiceBase<TContent>` — the same tier `GetByIdAsync` already lives on. The user caught this: "you moved it from the IContentService to the IAsyncContentService base, are you sure that's correct? Since it'll then spill over to media service AND member service when we migrate those." They were right: `IMediaService`/`IMemberService` implement only the narrow `IContentServiceBase<TItem>` (which declares just `GetById(Guid)` + `Save` — genuinely shared, so `GetByIdAsync`'s placement on the wide tier was correct). But sync `GetByIds(IEnumerable<Guid>)` has always lived on the narrower `IPublishableContentService<TContent>` (Document + Element only, via the `TContent : IPublishableContentBase` constraint) — Media/Member never had it. Moving `GetByIdsAsync` to `IAsyncPublishableContentService<TContent>` fixed it.

**Why:** this codebase's async interface tiers (`IAsyncContentServiceBase<TContent>`/`IAsyncPublishableContentService<TContent>` — the former later renamed, see [[project_document_repository_retirement_plan]]) are deliberately built as a 1:1 mirror of the existing sync tiers (`IContentServiceBase<TItem>` vs. `IPublishableContentService<TContent>`). Placing a new async member by pattern-matching "where did the last one go" instead of "where does its sync counterpart live" breaks that mirror silently — the compiler won't catch it, since both tiers are valid interfaces to add a method to. The wide tier is what `IMediaService`/`IMemberService` will eventually need to implement when they get their own async EF Core repositories; the narrow tier is Document/Element-only forever, since Media/Member have no publish workflow.

**How to apply:** Before declaring a new `*Async` member anywhere in this interface hierarchy, find its exact synchronous counterpart first and check which specific interface declares it — `grep` the method name across `IContentServiceBase.cs`, `IPublishableContentService.cs`, and each concrete service's own interface (`IContentService.cs`, `IMediaService.cs`, etc.), don't assume. If the sync method is on the narrow/shared tier, the async one goes on the wide async tier. If it's on the publish-specific tier (or doesn't exist as a shared interface member at all — e.g. it's only ever been a concrete method on `PublishableContentServiceBase<TContent>`, itself only inherited by Element, never Media/Member), the async one goes on the narrow async tier. After adding a member, it's worth a final sanity check: would `MediaService`/`MemberService` structurally be able to implement this if asked to today (do they derive from a base that has the sync equivalent at all)? If not, it doesn't belong on the wide tier.
