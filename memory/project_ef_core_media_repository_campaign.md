**Key facts found while planning (verified 20-11-2026):**
- Media is non-publishable: tables node/content/contentVersion/mediaVersion(id, path); no entity table, no culture variations; media types are invariant.
- `MediaService` is the only consumer of `IMediaRepository`; `IMediaService` has ~75 src call sites in 30 files (Core, Infrastructure, Api.Management, Search.Core only) and ~287 integration call sites (156 are `Save`); 20 of its 49 members have no caller outside `MediaService`. HybridCache and the Delivery API do not use it.
- Media baseline is fully green (562 unit + 697 integration tests named Media), so no PR 0.
- Parity list (§4b): `IsSorting` on the sort saving notification (#24349 handlers skip metadata extraction), one `MediaDeletedNotification` per item deepest-first (deletes files), `MediaRefreshNotification` from the repository, `umbracoMediaVersion.path` from `umbracoFile` via `MediaUrlGeneratorCollection`, tags on every save, version delete is a no-op, Guid-v7 + duplicate-key checks on single save, `DeleteMediaOfTypes` trashes all non-matching descendants, no relation check when emptying the bin.
- Hazard once PR 6 merges: upstream fixes to the sync `MediaService`/`MediaRepository` must be walked by hand into the async twins on every merge from main ([[project_async_fork_merge_hazard]]).

**Decisions confirmed by the user on 20-11-2026 (§8; PR 1, PR 2 and PR 5 unblocked, none started):** media-only scope (members next), hoist-first in both tiers, tree operations on the wide service base (ElementService inherits them), engine semantics replace media's exceptions/ignored cancels, no relation check on empty-recycle-bin for media, the four file-system members of IMediaService stay sync, `GetMediaByPathAsync` kept though uncalled, `CountNotTrashed` dropped.

**Why:** the user asked for the media migration planned the same way as elements, with the branch's contract rules (no ids, no IQuery, async everywhere, Attempt pattern) and the content repository/service as the template.

**How to apply:** follow CAMPAIGN.md §6 every PR, including the two status.json/board updates; a hoist PR is verified by the document/element fixtures at unchanged counts plus a normalised method diff, not by red-first tests.

**23-11-2026 (PR 2 review, user decision):** do not put `GetByLevelAsync`, `GetAncestorsAsync` or `RecycleBinSmellsAsync` on `IAsyncContentRepository`. Elements live in containers, so their ancestors and levels are container concepts, and a trashed container with elements inside makes the element bin non-empty without any element directly under it; the element campaign kept the three off `IElementRepository` for that reason. They live on the wide base as protected cores (`*CoreAsync`) and are exposed per kind: `IDocumentRepository` today, `IAsyncMediaRepository` in PR 4. `GetAncestorsCoreAsync` filters the path ids by the repository's own object type (the recycle bin and containers sit on paths but are not ancestors of the kind) and returns empty for a key of another kind. The wide tier otherwise keeps the NPoco shape (versions and recycle bin for every kind) until the members campaign decides a split.

**24-11-2026 (PR 3, branch `v20/feature/ef-core-media-repository-3-hoist-write-path`, stacked on PR 2 at `1d880d7b519`):** one scripted transplant (`scratchpad/pr2/phase3.py`). Wide base owns a non-publishing `PersistNewItemAsync`/`PersistUpdatedItemAsync`, the generic `PersistDeletedItemAsync`, invariant naming, and protected steps (`PersistNewNodeAsync`, `PersistNewContentAsync`, `PersistNewVersionAsync`, `PersistNewPropertyDataAsync(db, item, publishedVersionId)`, `PersistUpdatedPropertyDataAsync`, `GetCurrentVersionRowAsync`, `ApplyParentChangeAsync`, `UpdateNodeRowAsync`, `UpdateContentRowAsync`, `UpdateVersionRowsAsync`); the publishable base overrides the two persist methods composing them, deletes `ContentSchedules` before calling the base delete, and adds the variant naming step in a three-arg `SanitizeNamesAsync`. Flags are plain parameters, not an options record (`publishedVersionId` changes mid-persist, `publishing` differs per call). Publishable base 1478 → 1107 lines. Review found two media behaviour differences: the wide update early-returns when nothing is dirty (NPoco media always writes; the user accepted this as a media change, §4b 7), and the new-item sort order (NPoco media and members always take the next free one, documents keep an explicit one). The user wanted NPoco parity for the second, so it is a hook: `ResolveNewItemSortOrderAsync` on the wide base defaults to the next free sort order and the publishable base overrides it with the document rule. Rule from PR 2 and PR 3: where NPoco kinds differ, keep it per kind through a hook, never pick one kind's rule for the wide base. Unit 8239, integration suite 1353 green on SQLite.
